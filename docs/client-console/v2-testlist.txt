Matrix3 Client Console V2 - consolidated deferred runtime acceptance list

Run this list after pulling the accumulated V2 bundle. It supersedes old home-page/Commands/Owner presentation checks that refer to the removed Shell foundation, focus-test scaffold, 304-button command wall, or Owner-hosted RoTS research. Use the detailed legacy testlist.txt or specialist Client Atlas/BossLabs test lists only if one of these checks exposes a deeper regression.

1. Start Matrix3 normally in Eclipse/Java 8. Confirm the game renders/logs in normally and the Client Console opens beside the game without Canvas/Swing flicker, focus loss, or input regression.
2. Inspect the rail. Confirm Home, Owner, Commands, Player, Items, Client Atlas, Boss Research, and Settings use recognizable centered icons; tooltips identify each icon; selected/hover/pressed states remain obvious; clicking the active icon still collapses the panel.
3. Open Home before login. Confirm the MATRIX3 Developer dashboard shows waiting/read-only values rather than throwing errors or attempting gameplay/server mutation.
4. Log in with Home visible. Confirm Display name, Rights, Client state, Tile, Plane, and Region populate automatically and refresh while the dashboard is visible.
5. Walk several tiles and cross/teleport across a region boundary with Home visible. Confirm Tile/Plane/Region follow the same values as the Player panel and update without rebuilding the dashboard.
6. Switch away from Home, move in game, then return. Confirm dashboard values refresh immediately and there is no visible background-refresh/render hitch while Home is hidden.
7. Confirm the old `Shell foundation`, Docking instructions, and permanent Focus test field are gone from Home. Focus/input regression should instead be tested through real text fields such as Commands search/arguments, Item Browser search, Boss Research IDs/notes, and Client Atlas search.
8. Resize the console from its minimum practical width through a wide layout at 1280x720, 1600x900, 1920x1080, and ultrawide where available. Confirm Dashboard, Owner, Player, Settings, Commands, and Boss Research remain reachable with vertical scrolling and the game view still respects the existing minimum width.
9. Test at 100%, 125%, and 150% Windows display scaling where available. Confirm rail icons, shared headers/cards/value rows/status text, wrapped Settings/Boss Research copy, fields, and buttons remain readable without overlap or missing controls.
10. From Dashboard, open BossLabs. Confirm it launches normally as the existing separate developer window and the Client Console remains responsive.
11. From Dashboard, open RS3 CacheEditor. Confirm it uses the existing external Server-side launcher, reports launch status, suppresses duplicate launch requests while already running, and does not block the client.
12. Use Reset Client Console Layout from Dashboard. Confirm the existing workspace authority resets window/console geometry, returns Home as appropriate, and the reset state survives a clean restart.
13. Item Browser: type a broad partial name and stop typing. Confirm results refresh after about 500ms (not the previous 1.25 seconds), broad matches remain complete, empty browse remains capped at 160, context menus retain the dark Client Console styling, and thumbnail/game rendering stays responsive.
14. Open Commands. Confirm the old wall of individual command buttons is gone and the palette shows one scrollable result list with command name, category, usage, and a visible warning mark for protected commands.
15. In Commands search, type `tele`, `item`, `gfx`, and a usage fragment such as `itemId`. Confirm filtering is immediate, case-insensitive, searches name/category/usage, keeps the category filter working, and does not visibly hitch the game.
16. Keep focus in Commands search. Use Up/Down to move the highlighted result, Enter to select it into the composer, and Esc to clear search. Confirm these keys do not leak movement/hotkeys into the game. Click a result with the mouse and confirm it selects the command but does not execute it.
17. Select `::item`, enter `4151 1` in Arguments, confirm Preview becomes `::item 4151 1`, then press Enter in Arguments. Confirm the command queues through the existing ClientConsoleBridge/normal Matrix3 server command path and behaves exactly like the prior Commands panel.
18. Select `::shutdown` or another protected command. Confirm the first Run/Enter attempt changes the action to Confirm Run and does NOT execute. Let five seconds expire and confirm a later attempt again requires a fresh first confirmation. Do not perform the second confirmation unless intentionally testing the destructive command.
19. Open Boss Research before login. Confirm it lazy-creates as its own panel, the panel can scroll at narrow width, RoTS definition readiness is shown without starting a scan automatically, and no command/gameplay mutation occurs merely by opening it.
20. Log in, select several RoTS brothers, and confirm the selected brother/NPC ID and saved-finding view update. Use Become NPC/Reset Appearance only if you intend to test the existing research command bridge; confirm normal server command authority remains in control.
21. In Boss Research, enter a known animation/GFX ID and use Play/+/−/Stop as applicable. Confirm probes use the existing `ClientConsoleBossResearchBridge` command queue, the UI stays responsive, and choosing/playing a probe prepares the corresponding finding asset fields without auto-saving evidence.
22. Save one harmless Boss Research finding with a clear confidence classification and note. Switch brothers and return. Confirm the finding reloads from the existing Boss Research findings store and no unrelated player/game state is persisted by the panel.
23. In Boss Research cache evidence, run Scan RoTS and Deep Scan. Confirm both run off the Swing thread, Scan/Deep Scan buttons disable during work, output remains copyable/clearable, the prior RoTS evidence content is still available, and Deep Scan keeps the existing readiness/failure semantics. This verifies the old Owner research workflow was migrated without feature loss.
24. Open Owner. Confirm it now contains Account plus owner-tool guidance only; Boss Research and RoTS Scan/Deep Scan controls must not be duplicated in Owner. Display name, Rights, and Client state must still refresh while Owner is visible.
25. Open Settings at the minimum practical console width. Confirm Game modes, Quality of life, and Dev Mode cards track viewport width, wrapped descriptions remain readable, and existing toggle/apply behavior is unchanged.
26. Open Client Atlas once from the rail and return to other panels. Confirm the Atlas panel still lazy-loads through its existing panel ID/icon and the Boss Research addition did not replace, reorder incorrectly, or break Atlas persistence/navigation. Use the dedicated Client Atlas test list for deeper Atlas acceptance.
27. Run one safe Commands action, one Item Browser Inventory spawn, one Item Browser Bank spawn, and one Settings apply. Confirm all existing bridges/permissions remain authoritative and Commands.java behavior is unchanged.
28. Rapidly switch Home/Owner/Commands/Player/Items/Atlas/Boss Research/Settings while moving in game, resizing the console, searching Commands/Items, and typing into console fields. Confirm no panel is rebuilt unnecessarily, focused console text fields do not leak movement/hotkeys into the game, and returning focus to the game restores normal controls.
29. Leave Boss Research selected, cleanly close Matrix3, and relaunch. Confirm Boss Research restores as the active panel through the existing active-panel string preference. Repeat once with Atlas or another panel to confirm existing active-panel persistence remains general rather than Boss-specific.
30. Final clean restart: confirm window position/size/state, console open/collapsed state, console width, and active panel restore correctly after the full V2 finish bundle.

Pass condition: V2 looks and feels intentionally designed, Boss Research has one coherent dedicated home, Owner is no longer a boss-tool junk drawer, and Matrix3 gameplay, renderer ownership, command authority, panel persistence, permissions, specialist bridges, and client-thread ownership remain unchanged.
