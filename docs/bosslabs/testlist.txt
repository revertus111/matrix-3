Matrix3 BossLabs - planned runtime acceptance list

Documentation-only baseline
1. Confirm docs/bosslabs/BOSSLABS.md remains subordinate to AGENTS.md, docs/rs3/PROJECT.md, and docs/client-console/CLIENT_CONSOLE.md.
2. Confirm BossLabs does not claim ownership of combat, NPC lifecycle, world state, drops, permissions, persistence, or other Matrix3 gameplay authorities.
3. Confirm new BossLabs work is driven by the first complete custom boss rather than speculative tool expansion.

BossLabs external-window acceptance once implemented
4. Open BossLabs through its approved launcher path. Confirm the Matrix3 client continues rendering and receiving input normally.
5. Confirm BossLabs uses the intentional Client Console dark visual system and does not present unfinished default Swing styling.
6. Resize BossLabs at practical non-maximized sizes. Confirm important controls remain reachable through layout reflow/scrolling and are never clipped off-screen.
7. Test common Windows display scaling targets (100%, 125%, 150%). Confirm text remains readable and controls do not overlap or disappear.
8. Type W/A/S/D and other game hotkeys in BossLabs text fields. Confirm the game does not also consume those keys. Return focus to the game and confirm normal input resumes.
9. Move/resize BossLabs, close it cleanly, and reopen/relaunch when geometry persistence exists. Confirm valid window geometry restores and invalid/off-screen geometry is clamped safely.
10. Repeatedly resize/move the BossLabs window. Confirm preference writes are quiet/coalesced and do not cause visible client hitching.
11. Trigger any intentionally testable panel/definition validation failure. Confirm the tool reports the problem without crashing the running game client where practical.

First-boss runtime acceptance
12. Spawn the first boss through the authoritative Matrix3 development path and confirm normal NPC lifecycle/pathing remains Matrix3-owned.
13. Verify the boss can execute its minimal Phase 1 attack loop without BossLabs directly owning combat calculations.
14. Verify projectile, AoE, hazard, targeting, minion, and timed mechanics individually as they are added; classify runtime-proven behavior as VERIFIED.
15. Force common HP thresholds/phases through safe development controls and confirm phase transition/cleanup behavior matches the encounter definition.
16. Reset the encounter repeatedly. Confirm boss state, minions, hazards, timers, targets, and temporary encounter objects clean up without leaking into the world.
17. Kill the boss normally. Confirm death/cleanup and reward/drop behavior routes through Matrix3-owned systems.
18. Relaunch/reload the same boss definition after persistence/storage support exists and confirm the saved definition reproduces the intended encounter configuration.
19. Run the relevant Matrix3 smoke-test portion after any meaningful engine/runtime extension. Core ownership regressions are blockers.

Framework acceptance after boss #1
20. Create a second small boss/encounter using the proven reusable framework. Confirm it can reuse definitions/components without copying boss #1's encounter implementation wholesale.
